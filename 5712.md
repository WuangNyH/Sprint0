# Quy trình code, lập trình và Quy định ghi log task & nội dung cần thực hiện trước khi release

# 🚀 I. Quy trình Code, Lập trình

## 1. Code & Lập trình

### 1.1. Quy tắc code chung

* **Branching model:** sử dụng Gitflow hoặc GitHub Flow

  * `main` → nhánh ổn định (release).
  * `develop` → nhánh phát triển.
  * `feature/*` → nhánh cho từng tính năng.
  * `hotfix/*` → sửa bug khẩn cấp.
* **Code convention:**

  * Backend (Java Spring Boot)
  * Frontend (Vue.js)
* **Commit message:** dùng chuẩn [Conventional Commit] (ví dụ: `feat: add user login API`, `fix: bug UI hiển thị`).

### 1.2. Code Review

* Mọi feature/bugfix đều phải tạo **Pull Request (PR)**.
* Ít nhất 1–2 reviewer approve trước khi merge.
* Reviewer check:

  * Code clean, dễ đọc.
  * Không duplicate logic.
  * Unit test đầy đủ.

---

## 2. Build & Test

### 2.1. Backend (Java Spring Boot)

* Dùng **Maven/Gradle** để build.
* Pipeline:

  * `mvn clean install` hoặc `gradle build`.
  * Chạy **JUnit test** + kiểm tra coverage (JaCoCo).
  * SonarQube scan (nếu có) để check quality gate.

### 2.2. Frontend (Vue.js)

* Dùng **npm hoặc yarn**.
* Pipeline:

  * `npm install`
  * `npm run build` (tạo ra thư mục `dist/`).
  * Chạy test: `npm run test` (nếu có unit test với Jest).

---

# 📘 II. Quy định ghi log task & nội dung cần thực hiện trước khi release

## 1. 🎯 Mục tiêu

* Đảm bảo **tính minh bạch** trong quá trình phát triển.
* Giúp team và PO (Product Owner) **theo dõi đầy đủ** tiến độ, công việc đã hoàn thành, công việc còn tồn đọng.
* Giảm thiểu **rủi ro khi release** bằng cách có đầy đủ log task, checklist rõ ràng.

---

## 2. 📝 Quy định ghi log task

1. **Mỗi task phải được ghi nhận đầy đủ trên hệ thống quản lý công việc** (Jira, Trello, ClickUp, hoặc tool được team thống nhất).

2. Log task cần bao gồm:

   * **ID**: Mã định danh task (VD: `TASK-123`)
   * **Title**: Tên ngắn gọn, dễ hiểu.
   * **Description**: Nội dung chi tiết cần thực hiện.
   * **Acceptance Criteria**: Điều kiện để task được coi là hoàn thành.
   * **Assignee**: Người thực hiện.
   * **Status**: To Do / In Progress / Code Review / Done.
   * **Estimate**: Thời gian ước lượng (story points hoặc giờ).
   * **Log Time**: Thời gian thực tế đã dùng (nếu áp dụng).
   * **Link**: Liên kết đến Pull Request / Merge Request / Tài liệu liên quan.

3. **Comment log**: Tất cả thay đổi, vấn đề phát sinh, quyết định kỹ thuật cần được ghi lại trong phần comment.

---

## 3. ✅ Nội dung cần thực hiện trước khi release

Trước khi phát hành (release), team cần thực hiện và ghi log theo các hạng mục sau:

### 3.1. Kiểm tra Task & User Story

* Đảm bảo **100% task trong Sprint Backlog** đã chuyển sang trạng thái `Done`.
* Kiểm tra lại **Definition of Done (DoD)** cho từng User Story:

  * Code đã được merge vào branch chính (develop/master).
  * Code đã được review (Code Review xong).
  * Unit test & Integration test đạt yêu cầu.
  * Không còn bug blocker/critical.
  * Document (nếu có) đã được cập nhật.

### 3.2. Kiểm thử & chất lượng

* ✅ Regression test trên môi trường staging.
* ✅ Tài liệu test case / kết quả test được log lại.
* ✅ Đảm bảo hệ thống build & pipeline CI/CD chạy thành công.

### 3.3. Checklist Release

* 📌 Ghi lại **phiên bản release** (version, tag Git).
* 📌 Ghi log **các tính năng mới** (new features).
* 📌 Ghi log **bug fix** đã hoàn thành.
* 📌 Ghi log **công việc còn tồn đọng** (nếu có, chuyển sang backlog).
* 📌 Chuẩn bị **Release Note** cho PO/Stakeholder.

---

* [x] Pipeline CI/CD pass ✅

## 5. 📌 Lưu ý

* Tất cả thành viên Scrum Team đều có trách nhiệm ghi log chính xác.

* PO cần xác nhận nội dung release note trước khi phát hành chính thức.
